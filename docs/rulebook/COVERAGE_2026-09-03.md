# Rule test coverage — measured, 2026-09-03

Closes retrospective finding #6 (lane R4a):
`docs/audits/2026-09-02-retrospective/RETROSPECTIVE.md` §6 found that
`docs/rulebook/README.md` — generated by `scripts/generate-rulebook.ts`, the
"machine-counted authority" — asserted every rule constant is "fire-tested
and no-fire-tested" as a hardcoded sentence at roughly line 575 of the
generator. That was never measured. 21 of the ~3,187 rule constants had zero
occurrence anywhere under `tests/`, all live: `ACT1_TOO_LONG`,
`FLAT_CHARACTER_ARC`, `TONAL_WHIPLASH`, `NO_DIALOGUE`, and 17 others.

## Method

`scripts/measure-rule-test-coverage.mjs` is the measurement. It:

1. Enumerates every rule constant using `extractAllPasses` from
   `scripts/generate-rulebook.ts` — the same source-of-truth the rulebook
   generator itself uses, so there is one enumeration, never a second regex
   that could drift from the first.
2. For each distinct rule-constant name, counts word-boundary matches
   (`\bRULE_NAME\b`) against every file under `tests/**` (any extension —
   fixtures and helpers count, not just `*.test.ts`).
3. Writes `docs/rulebook/coverage.json` (per-rule occurrence counts and file
   lists, totals, and the zero-occurrence list) and prints a human summary.

`npm run rulebook` now runs this measurement first, then
`scripts/generate-rulebook.ts`, which reads `docs/rulebook/coverage.json` and
renders the true count into `docs/rulebook/README.md` — the hardcoded
"fire-tested and no-fire-tested" sentence (and the retired
per-wave-acceptance-checklist text it cited) is deleted. If the coverage
report is missing, the generator refuses to render rather than falling back
to a claim.

`tests/core/rule-test-coverage.test.ts` is the CI tripwire: it fails if the
zero-occurrence list is ever non-empty again, and fails if
`docs/rulebook/README.md`'s published coverage sentence drifts from a fresh
measurement (the same freshness-check pattern `tests/core/rulebook.test.ts`
already used for the total-rule count).

**Caveat, stated honestly:** a word-boundary name match is a coverage proxy,
not proof that the referencing test is behavioural or asserts on the
finding. It is exactly the same kind of proxy the retired hardcoded sentence
implicitly claimed to have already satisfied for every rule — this work
makes it a real, re-runnable measurement instead of an assertion, and (per
the retrospective's actual finding) hand-verifies every rule this
measurement had previously missed with a real fire/no-fire test, not merely
a name mention.

## The 21 rules that had zero test reference

the rule, negative fixture that doesn't, asserting on `result.issues`
content — not shape-only). None turned out to be dead or unreachable from the
live pipeline; all 21 fire under a real triggering fixture. **No KNOWN
WEAKNESS entries** — see "Known weaknesses" below for what that would have
looked like if one had been found.

## Known weaknesses

None found. Every one of the 21 previously-untested rules fired under a
constructed fixture that matches its actual guard conditions in
`server/nvm/revision/passes/*.ts` — none turned out to be dead code or
unreachable from the live pipeline. Had one been found unreachable, the
disposition per the task brief would have been: keep the rule constant (no
deletion — that is a separate approved migration), write a test that
documents the current (non-firing) behavior, and mark it
`// KNOWN WEAKNESS:` with what was found, both in the test and listed here.
